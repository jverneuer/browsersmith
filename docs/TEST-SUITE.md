# @browsercore/testing — Test Suite Specification

> Canonical, source-of-truth specification for the `@browsercore/testing` package.
> Every test case the monorepo must satisfy lives here, organized into 17
> categories. The implementation in `packages/testing/src/categories/` models
> these categories as typed constants and vitest stubs; this document is the
> reference those stubs point at.

## Purpose

`@browsercore/testing` exists to prove that the protocol stacks (`@browsercore/tls`,
`@browsercore/http1`, `@browsercore/http2`, `@browsercore/cookies`, `@browsercore/profiles`,
`@browsercore/fetch`) behave **identically to a selected real browser** — and that
this equivalence is never silently broken. The 17 categories below progress from
low-level byte correctness up through real-world interoperability and regression
guards.

## Layered philosophy

Tests are layered so cheap, deterministic checks run on every push and expensive,
network-dependent checks run on demand / in CI:

1. **Unit** — pure functions (byte helpers, serializers). Always run.
2. **Serialization** — golden packet comparison against recorded browsers. Run on demand + CI.
3. **RFC compliance** — protocol-conformance suites (RFC 8446, 9113, 9110). CI.
4. **Reference comparison** — compare our wire output against a reference implementation. CI.
5. **Real-world compatibility** — interoperability against public servers. On demand.
6. **Performance benchmarks** — latency/throughput, tracked over time. On demand / nightly.

## Test Category 1 — TCP Transport

Verify transport layer behaves correctly.

- TCP connection establishment
- Connection timeout handling
- Read buffering
- Partial packet handling
- Large packet handling
- Connection reuse
- Graceful shutdown
- Unexpected disconnect handling
- IPv4 support
- IPv6 support

**Expected:** identical application-visible behavior compared to Node's transport.

## Test Category 2 — TLS Serialization

Verify every generated TLS message is correct.

- ClientHello serialization
- ServerHello parsing
- Extension parsing
- Record fragmentation
- Finished message generation
- Alert handling
- Key schedule generation
- Session resumption

**Expected:** generated packets conform to the TLS specification.

## Test Category 3 — Browser Profile Comparison

Verify browser profile correctness. Each browser profile compared against a
packet capture from a reference implementation.

ClientHello comparison verifies:

- TLS version
- Cipher suite list + ordering
- Extension ordering
- Supported groups
- Key shares
- Signature algorithms
- ALPN list
- GREASE values
- Session ID length
- Compression methods
- PSK extension
- Padding extension
- SNI extension
- Record version
- Record fragmentation

**Acceptance:** every configurable field matches the selected browser profile.

## Test Category 4 — TLS Fingerprint

Verify observable TLS fingerprint matches the selected browser profile.

- JA3 fingerprint
- JA4 fingerprint (where applicable)
- ALPN negotiation
- Negotiated cipher suite
- Negotiated protocol version
- Supported signature algorithms
- Supported elliptic curves

**Acceptance:** fingerprint generated by the project matches the configured profile.

## Test Category 5 — HTTP/1.1

Verify HTTP behavior.

- Header serialization
- Header ordering
- Connection reuse
- Chunked encoding
- Compression
- Redirect handling
- Cookie handling
- Keep-Alive behavior

Compare against reference implementation.

## Test Category 6 — HTTP/2

Ensure HTTP/2 behavior matches the selected browser profile. Compare:

- SETTINGS values
- SETTINGS ordering
- SETTINGS ACK timing
- WINDOW_UPDATE values
- Frame ordering
- PING handling
- GOAWAY handling
- Stream prioritization (where implemented)
- HPACK behavior
- Pseudo-header ordering

**Acceptance:** generated frame sequence matches the reference implementation
within documented protocol tolerances.

## Test Category 7 — Header Profiles

Each browser profile defines default headers. Verify:

- User-Agent
- Accept
- Accept-Language
- Accept-Encoding
- Cache-Control
- Upgrade-Insecure-Requests
- Sec-CH-UA
- Sec-CH-UA-Mobile
- Sec-CH-UA-Platform
- Fetch Metadata headers
- Header ordering

## Test Category 8 — Cookie Behavior

Verify cookie parsing and policy.

- Cookie parsing
- Expiration
- Secure cookies
- HttpOnly
- SameSite
- Domain matching
- Path matching
- Cookie ordering

Compare against browser behavior.

## Test Category 9 — Compression

Verify gzip, brotli, deflate — ensure identical decoding behavior.

## Test Category 10 — Redirect Handling

Verify 301, 302, 303, 307, 308.

- Method rewriting
- Header preservation
- Cookie persistence
- Maximum redirect count

## Test Category 11 — Session Resumption

Verify TLS session resumption.

- TLS session tickets
- Session cache
- Resumed handshake
- Ticket expiration

## Test Category 12 — Connection Reuse

Verify connection reuse behavior.

- Keep-Alive
- HTTP/2 multiplexing
- Connection pooling
- Idle timeout
- Maximum streams

## Test Category 13 — Error Handling

Verify behavior under invalid / adversarial conditions.

- Invalid certificates
- Unsupported cipher
- Unexpected alerts
- Truncated packets
- Invalid HTTP responses
- Timeout handling
- Broken TCP connections

## Test Category 14 — Packet Capture Comparison

Compare raw packet captures against the reference implementation. For each
supported browser profile:

1. Generate a capture using the reference implementation.
2. Generate a capture using this project.
3. Compare protocol-level behavior.

Compare:

- TLS records
- HTTP frames
- Header order
- Extension order
- Packet sizes
- ALPN
- Timing-independent message sequence

**Acceptance:** generated protocol sequence matches the reference except for
fields intentionally randomized by protocol specs (ephemeral keys, nonces,
GREASE values when randomized).

## Test Category 15 — Real World Compatibility

Verify interoperability with a representative set of public servers. Examples:

- Static websites
- HTTP/2-only servers
- CDNs
- Reverse proxies
- TLS 1.2-only servers
- TLS 1.3 servers
- Servers with large certificate chains

**Acceptance:** connections succeed and behave consistently with the reference
implementation under equivalent configuration.

## Test Category 16 — Regression Tests

Every discovered protocol issue should produce a permanent regression test
including:

- Serialized packets
- Expected parser output
- Expected state transitions
- Expected network behavior

**Acceptance:** no previously fixed issue should reappear unnoticed.

## Test Category 17 — Performance Benchmarks

Measure and track over time:

- Handshake latency
- Requests per second
- Memory usage
- CPU usage
- Packet allocation
- TLS throughput
- HTTP/2 throughput

**Acceptance:** benchmarks are tracked over time to identify regressions.

## Continuous Validation

Every PR should automatically execute:

- Unit tests
- Serialization tests
- RFC compliance tests
- Packet comparison tests
- Browser profile validation
- Interoperability tests
- Performance benchmarks (where practical)

Changes affecting protocol output should require updated golden captures and
explicit review of behavioral differences.

## Definition of Success

A browser profile is **complete** when:

1. All unit tests pass.
2. TLS serialization matches the profile spec.
3. HTTP behavior matches the configured profile.
4. Packet captures are equivalent to the chosen reference (accounting for
   expected randomized fields).
5. The client interoperates reliably with diverse real-world servers.
6. No unexpected regressions are introduced by future changes.

**Overall objective:** every protocol layer is verifiable, reproducible, and
observable — providing high confidence the stack behaves consistently with its
selected browser profile while remaining standards-compliant and maintainable.
